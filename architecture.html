The architecture behind agent identity.

Beyond the concepts: how Microsoft Entra Agent ID is meant to be deployed, why each design decision exists, and how blueprints, agent identities, the auth sidecar, and token claims map onto real systems you build and operate.

Design rationale

Why agents get their own identity

The whole model exists to fix two failure modes engineers hit when bolting auth onto agents. Understanding the failure modes explains every later decision.

✗ Anti-pattern

Hard-coded secrets in agent code

Every agent image carries a copy of the app's client_secret. One log leak, compromised image, or stray .env in Git exposes the whole tenant.

✓ Each agent gets its own Entra identity; credential handling moves out of agent code.
✗ Anti-pattern

Delegated user tokens for everything

The agent can only act when a human is present, and every call looks like the same service principal — you lose per-agent auditability.

✓ Autonomous flows + per-agent identities give individual attribution in sign-in & audit logs.
⚖️ The trade-off it buys

Identity as a governance unit

A blueprint gives even a single agent consistent Conditional Access, monitoring, governance, and audit entries — the same infrastructure multi-agent systems need.

✓ Minimal setup now; no re-architecture when you scale to many agents.
Reference deployment · the auth sidecar

Keep credentials out of your agent code

The Microsoft Entra Auth SDK ships as a sidecar container that runs next to your agent and owns every token operation — client-credentials, FIC, OBO, caching, refresh — so your code never touches a secret.

New to the term "sidecar"? It's a small helper container that's deployed right alongside your main application — think of a motorcycle sidecar riding next to the bike. The two run side by side, share the same local network, and start and stop together, but stay separate programs. Here, the sidecar's single job is handling identity and tokens, so that messy, security-sensitive logic lives outside your agent's own code.

HTTP endpoints your agent calls

GET · autonomous (app-only)
/AuthorizationHeader/{service}?AgentIdentity={id}

Returns a ready-to-use Authorization header with an app-only token for the named agent identity.

GET · agent's user account
/AuthorizationHeader/{service}?AgentIdentity={id}&AgentUserId={oid}

Token via the agent's own user account. Provide AgentUserId or AgentUsername — never both.

GET · interactive (OBO)
/Validate → /AuthorizationHeader/{service}

Validate the incoming user token first, then get an on-behalf-of header passing the user's bearer token.

GET · proxied call
/DownstreamApi/{service}

The sidecar acquires the token and makes the downstream call for you in one hop.

How many blueprints & identities?

Deployment patterns explorer

The number of blueprints and agent identities you create is an architecture decision driven by trust boundaries and attribution. Pick a pattern to see how it maps.

🧱 Trust boundary = the shared risk surface where one compromise is assumed to affect the whole perimeter. Agents on separate runtimes, secrets, and network segments don't share a trust boundary — and crossing a trust boundary means a separate blueprint. This is a threat-modeling decision you make, not one Entra makes for you.
Patterns to avoid

Don't create identities you don't need

Directory-level identities are for accountability and access control — not for runtime scale or data partitioning. These three over-uses add objects and overhead with no security benefit.

🔁 Scale-out replicas

Running N copies of the same agent code is a runtime concern. All replicas run under the same agent identity simultaneously. A per-replica identity adds directory objects with zero audit or access benefit.

🧠 Memory & context isolation

Agent memory is usually a shared store (Redis, AI Search) filtered by session ID at retrieval. Access is controlled by the agent identity's permissions — separate identities per session add complexity, not security.

📄 Per-object identities at scale

One identity per meeting / document / ephemeral object at high volume isn't practical today. Use shared identities and distinguish interactions with session or context IDs at the app layer.
