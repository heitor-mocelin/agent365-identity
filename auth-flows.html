The three agent token-exchange flows, step by step.

Agents use OAuth 2.0 with specialized Federated Identity Credential (FIC) token exchanges. Every flow is a multi-stage chain where an agent identity blueprint impersonates its child agent identity. Step through each one and watch the actual HTTP requests, tokens, and validations.

Before you start · shared building blocks

Concepts every flow relies on

All three flows are built from the same primitives. Get these and the flows become easy to read.

🧬

Blueprint impersonates its agent

The agent identity blueprint (actor) obtains a token for its child agent identity (subject). A blueprint can impersonate many agents; an agent has exactly one blueprint.

🎫

FIC token exchange

The blueprint presents a credential and gets back T1 — a token-exchange token (Federated Identity Credential) used to act as the agent.

🛂

fmi_path

The agent identity's client ID. It tells Entra ID which child agent the blueprint is impersonating during the exchange.

🔑

Managed identity = preferred credential

Use a managed identity (UAMI) token TUAMI as the FIC. Avoid client secrets in production — prefer FIC or certificates.

🚫

No interactive flows

All agents are confidential clients. /authorize is never used — auth happens only via programmatic token exchanges.

🏛️

Single-tenant agents

Agent identities always operate within one tenant's security and policy boundaries, regardless of the blueprint's tenancy.
