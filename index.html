The core idea, in one line

An agent is treated like an employee 👤
It has a unique, persistent enterprise identity with privileges, authentication, roles, and compliance — just like a person.
Not a generic app registration ⚙️
Its identity is separate from human users and from ordinary application registrations, so it can be governed individually.

The three components

Blueprint → Instance → User

When you register an agent, these three identity components are created. Each builds on the previous one — a template, a deployment, and a runtime identity.

📋
COMPONENT 01

Agent blueprint

The agentic application — defines the agent's identity, permissions, and infrastructure. It's the template for creating instances.

  • Microsoft Entra app registration
  • Required Graph API permissions
  • Authentication configuration
  • Resource definitions (App Service, Web App)
Open detail →
🚀
COMPONENT 02

Agent instance

A specific deployment of your blueprint. Each instance gets its own identity and authentication footprint.

  • Unique Microsoft Entra agent ID
  • Service principal for authentication
  • Instance-specific configuration
  • Federated credentials for Teams
Open detail →
🧑‍💼
COMPONENT 03

Agent user

The runtime identity that appears in your org — a specialized subtype of user identity, designed for agents.

  • Full member of your M365 tenant
  • Own mailbox, OneDrive, people card
  • @mentionable across Microsoft 365
  • Immutable link to its parent instance

Deep dive · the agent user

Four things to understand about agent users

Agent users are full members of your organization, but with distinctive rules. Switch between the tabs to explore each facet.

🏷️

Marked as agentic

Flagged in the directory so it's distinguishable from human accounts.

🎫

Token type idtyp=user

Receives tokens with the user identity type, behaving like a user across services.

🆔

Unique Object ID

Has its own agent user ID, separate from the parent agent instance.

🚫

No traditional credentials

Can't have passwords, passkeys, or MFA factors of its own.

📞

Created via explicit API call

Must be created through an explicit call from the parent agent instance.

🔗

Immutable parent link

Permanently linked to its parent instance — it can't be re-parented.

🔄

Synced to the tenant

Synchronized into your Microsoft 365 directory like any member.

📜

License-assignable

Can receive M365 E5, Teams Enterprise, or Copilot licenses.

📬

Mailbox & OneDrive

Gets its own mailbox and storage, based on assigned licenses.

🌳

Org chart & people cards

Appears in the organizational chart and shows up in people cards.

@

@mentionable

Can be @mentioned in Teams, documents, and other M365 apps.

✉️

Unique principal name

e.g. agent@yourtenant.onmicrosoft.com.

Permissions & access control

Granular control at three levels

Permissions cascade from the blueprint down to the individual agent user, giving you layered, granular control over what an agent can do.

L1

Agent blueprint level

Defines the base permissions inherited by all instances created from the blueprint.

Broadest scope · template defaults
L2

Agent instance level

Specific permissions for the agent identity of a particular deployment.

Per-deployment scope
L3

Agent user level

User-specific permissions and access rights — the recommended identity for resource access.

Narrowest scope · user-like behavior

Default permission characteristics of agent users

✓ Managed via conditional access policies
✓ Exempt from MFA (no auth factors)
✓ Addable to Entra ID groups
✓ Member of  All Agent Users  group
✓ Access via explicit grants + licenses
💡 Tip: For agents that have an agent user identity, use the agent user identity primarily for resource access — it gives consistent, user-like behavior across Microsoft 365 services.

Lifecycle, end to end

From registration to cleanup

How the three identity components come into being and are eventually torn down — one continuous, auditable lifecycle.

1

Register the blueprint

Create the agentic application: Entra app registration, Graph permissions, auth config, and resource definitions.

2

Deploy an instance

A specific deployment gets a unique Entra agent ID, a service principal, and federated credentials for Teams.

3

Create the agent user

An explicit API call from the instance creates its single agent user child, with an immutable parent link.

4

Assign licenses & provision

License the agent user (E5, Teams, Copilot). Mailbox / OneDrive provision in ~10–15 min (up to 24h).

5

Operate (instant-on)

The agent acts via its own identity or on-behalf-of a user, governed by conditional access and explicit grants.

✕

Delete & cascade

Delete the parent instance and the child agent user is automatically deleted — clean teardown, full audit trail.
